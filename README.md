# chat2chara

把聊天记录变成一张能用的 AI 角色卡——**用真实数据的统计特征写，而不是凭印象编**。

**如果你手上有一份几万条的对话记录**，而现成的编卡器只能让你「描述一个人」——那描述不出那种味道。**这个工具是给你做的。**

![同一份语料，凭印象写 vs 跑了 analyze 再写](assets/compare-impression-vs-data.png)

左边是大多数角色卡的做法：写几个形容词。右边是这套工具的做法：先统计，再写。

**模型服从数字，不服从形容词。** 你写「偶尔用一下 [亲亲]」，它会理解成「经常用」；
你写「平均每 52 条才出现 1 次」，它才知道什么叫稀有。这就是这个项目的全部差别。

从一份聊天记录导出文件（或一份字幕），生成符合 `chara_card_v2` 规范的角色卡，导入 SillyTavern（酒馆）即可直接对话。

> 🧰 你需要的：**Python** · 一份聊天记录（或一份字幕）· 大约半小时

---

## 这个项目解决什么问题

现有的同类工具分成两条路，都不太适合「做一张真有那个人的味道的卡」：

**第一条是微调路线** —— 拿聊天记录去微调一个大模型。
效果上限高，但要显卡、要十几个 GB 显存、换个角色就得重训一次，而且最终产物是一个模型，不是一张卡。

**第二条是通用编卡路线** —— 各种 AI 编卡器。
它们的问题在于：**输入是「你的描述」**，你告诉它「这个人嘴硬心软、爱用叠词」，它就照着写。
可你脑子里对一个人的印象往往是失真的，凭印象写出来的卡，聊两句就崩。

**这个项目走第三条路：用真实记录的统计特征来写卡。**

不训练模型。不需要显卡。全部在本地跑，不调用任何 LLM，不花一分钱 token。

关键在于它统计的不是「你记得的样子」，而是**记录里真实的样子**——

举个例子。假如某个表情在全部 20 万条消息里只出现了 1200 次，那你凭感觉写「她偶尔用这个表情」是没用的，模型会把「偶尔」理解成「经常」。但如果你算出来**平均每 170 条消息才出现 1 次**，把这个数字直接写进角色卡的指令里，模型才知道什么叫稀有。

这个数字叫**摊薄率**。它是这个项目和其他方案最本质的区别。

## 工作流

两条素材都能进这条管道：**真人聊天记录**（JSON）走 `json2txt.py`，**动画 / 影视字幕**（.srt / .ass）走 `srt2txt.py`。从第二步开始完全一样。

```
聊天记录导出文件（JSON）
        ↓
   json2txt.py          规范化成统一管道格式
        ↓
    analyze.py           九维度全量统计（纯本地，核心）
        ↓
    sample.py            按时间分层采样连续片段
        ↓
   ┌─────────────────┐
   │  人工 / LLM 精读  │   ← 只有这一步用到 LLM，且是可选
   └─────────────────┘
        ↓
  角色卡 JSON（chara_card_v2）
        ↓
  validate_card.py       校验 + 结构检查
        ↓
   deploy_card.js        部署到 SillyTavern
        ↓
     酒馆里对话
```

**只有中间「精读」那一步需要 LLM，而且可以不要**——你可以自己读 `sampled.txt`，手工填卡。

## 快速开始

### 第 0 步：把项目拿到本地

**用 Git 的（推荐）：**

```bash
git clone https://github.com/cc66611/chat2chara.git
cd chat2chara
```

**不想用 Git 的：** 在仓库页面点绿色的 `Code` 按钮 → `Download ZIP`，解压到你喜欢的位置就行。

> 本项目**零第三方依赖**，不需要 `pip install` 任何东西——Python 自带的标准库就够了。
> 这是它跟同类方案最大的不同：**没有环境要配**。

### 第 1 步：先用假数据跑通（验证环境）

仓库自带一个生成器，能造出**完全虚构**的聊天记录（不含任何真实人物信息）。
先用它跑一遍，确认你的电脑没问题，再换成自己的数据。

**先进入脚本目录：**

```bash
cd scripts

# 1. 生成虚构数据（3000 条假消息，不含任何真实人物信息）
python make_demo_data.py -o ../examples/demo_chat.json -n 3000

# 2. 转成管道格式
python json2txt.py -i ../examples/demo_chat.json \
                   -o ../examples/demo_chat.txt \
                   --char-name "小鱼" --user-name "阿木"

# 3. 全量统计
python analyze.py -i ../examples/demo_chat.txt \
                  -o ../examples/demo_stats.txt \
                  --char-name "小鱼" --user-name "阿木"

# 4. 采样
python sample.py -i ../examples/demo_chat.txt \
                 -o ../examples/demo_sampled.txt --target 800
```


**每一步成功的样子：**

| 命令 | 你会看到 |
|---|---|
| 1 | `生成 3000 条虚构消息 -> ...` |
| 2 | `载入 3000 条，写出 3000 条，跳过 0 条` |
| 3 | `OK -> ...`，外加一行 `角色「小鱼」/ 本人「阿木」，共 3000 条` |
| 4 | `采样 ... 条（N 个月）` |

**跑完打开 `examples/demo_stats.txt`** —— 那就是一份完整的风格画像，也是这个项目要交给你的东西。

### 换成你自己的数据

**关于数据获取：**

本项目**不提供、不指导、不涉及**任何聊天记录的导出、解密或抓取手段。

请你自行确保你对自己正在处理的数据拥有合法权利（通常是你自己参与的对话），并遵守相应平台的服务条款与当地法律法规。**涉及第三方的记录，请务必取得对方知情同意。**

**但有一件事值得你知道：有些平台自己就带导出功能。**
这类导出的就是标准文件，不需要任何第三方工具，也不涉及任何解密——可以放心用：

| 平台 | 官方导出入口 | 产出 | 能不能直接接入 |
|---|---|---|---|
| **Telegram Desktop** | 设置 → 高级 → 导出 Telegram 数据 → 勾选「机器可读的 JSON」 | `result.json` | ✅ 直接能跑 |
| **QQ** | 消息管理器 → 导出消息记录 | txt / mht | ⚠️ 需先整理成 JSON |

> **微信不在这张表里。** 它从来没有提供过可读的导出功能——市面上所有「微信导出」工具都得去读它的加密数据库，
> 那正是本项目明确不碰的区域。这不是能力问题，是**边界问题**。

拿到文件后，把它整理成下面任一种结构，即可接入本管道：

```json
[
  { "time": "2024-03-01 20:15:00", "sender": "对方", "content": "在呢", "type": 1 },
  { "time": "2024-03-01 20:15:30", "sender": "我",   "content": "吃饭了吗", "type": 1 }
]
```

外层包一层 `{"messages": [...]}` 也能识别。字段名支持常见别名（`timestamp` / `createTime` / `from` / `text` / `msg` 等），具体见 `scripts/json2txt.py`。

不确定文件里有哪些发言人？先看一眼：

```bash
python json2txt.py -i your_export.json --list-senders
```

### 换成字幕（做二次元角色）

上面那条是「复刻某个真人」的路线。如果你要做的是**动画 / 游戏 / 小说里的角色**，
素材换成字幕就行——同一张卡、同一套统计，但**完全不涉及真人**。

```bash
# 1) 先看这份字幕里有哪些说话人（字幕通常带「名字：台词」前缀）
python srt2txt.py -i ../subs/ep01.srt --list-speakers

# 2) 转成管道格式。--date 给这一集打个日期
python srt2txt.py -i ../subs/ep01.srt -o ../subs/ep01.txt --date 2024-01-01

# 3) 几集合起来统计（后面和聊天记录路线一模一样）
python analyze.py -i ../subs/all.txt -o ../subs/stats.txt --char-name "星野"
```

**字幕来源的九维度，有一个要忽略：**

| 维度 | 对字幕 |
|---|---|
| [1] 消息长度 / [4] 表情 / [5] emoji | ✅ 一样有效 |
| [6] 口头禅 / [7] 高频词 / [8] 句尾 | ✅ 一样有效 |
| [9] 连发密度 | ✅ 一样有效 |
| [2] 每月消息量 | ⚠️ 变成「**每集台词量**」，能看出角色哪集戏份多 |
| [3] 活跃时段 | ❌ **无意义**——字幕时间戳是剧内时间，不是作息 |

九个维度里八个能用，写卡时跳过 [3] 就行。细节见 [docs/04-subtitle-source.md](docs/04-subtitle-source.md)。

> **边界**：字幕（动画 / 影视 / 广播剧）没问题。**游戏文本解包要避开**——
> 那涉及逆向工程，性质和「去读微信数据库」是一回事。

## 三条调优铁律

这三条是实测踩出来的，比脚本本身更值钱。

### 一、行数由示例决定，不由指令决定

**模型会严格模仿 `mes_example` 和 `first_mes` 的行数。**

如果你想让角色有「偶尔连发两三句」的效果，那么示例里每条回复就该控制在 5 行以内、`first_mes` 不超过 6 行。你要是示例里写了十行，模型就次次给你十行，指令里写「简短」也压不住。

指令里同时写死：**最多 3-5 行，宁少勿多，一次说不完就留到下一轮。**

### 二、表情要用摊薄率，不能用「偶尔」

**禁用不等于真实，摊薄率才等于真实。**

不要写「偶尔用 [微笑]」，要写：

> `[微笑]` 在全部记录里平均每 170 条消息才出现 1 次，绝大多数回复里禁止使用。

这个数字从 `analyze.py` 的输出里直接抄。模型对具体数字的服从度远高于对形容词的服从度。

### 三、抢戏必须用指令按死

不控制的话，模型会稳定地犯四个错：

- 自己演好几轮，不等你回复
- 自设时间流逝（「（过了一会）」「三秒后」）
- 替**你**说话
- 你还没回，就开始责怪你「怎么不回消息」

`post_history_instructions` 里必须有一条 **「一轮一停」** 规则，把这些逐条禁掉。

**另外：示例里绝对不能出现时间跳跃的示范**——模型会学。

## 接入国产模型（以智谱 GLM 为例）

> 先去 [open.bigmodel.cn](https://open.bigmodel.cn/) 注册，在控制台创建一个 API Key（新用户一般有免费额度）。

SillyTavern 里用 `Custom (OpenAI-compatible)`：

- URL：`https://open.bigmodel.cn/api/paas/v4`
- 模型：填你账号可用的模型名

**这里有一个坑值得单独说：新版本 GLM 系列会强制思考，导致延迟很高。**

试过但**不行**的写法：

- `thinking: { type: "disabled" }` → 直接报 400，错误码 1210
- `thinking: { effort: ... }` → 各档位照旧思考，没区别

**唯一有效的解法**是顶层参数：

```yaml
reasoning_effort: low
```

这时可以做到秒级直出、零思考过程。

问题是这个参数不在 SillyTavern 的转发白名单里，得手动注入：
**API 面板 → Connect 旁边的「Additional Parameters」→「Include Body Parameters」**，填上面的 YAML。

## 部署到 SillyTavern

> **还没装酒馆？** 先看官方安装文档：[docs.sillytavern.app/installation](https://docs.sillytavern.app/installation/)
> 大致三步：装 [Node.js](https://nodejs.org/zh-cn) → `git clone` 酒馆仓库 → Windows 双击 `Start.bat`。
> 装完浏览器打开 `http://localhost:8000` 就能进去。

```bash
node scripts/deploy_card.js -i 你的角色卡.json \
     -d "C:/SillyTavern/data/default-user/characters"
```

跑完之后有两件事必须做，**漏了会以为脚本没生效**：

1. **刷新页面**（F5）——SillyTavern 运行中不会重新扫描角色卡目录
2. **开一个新聊天**——旧聊天的历史里存着坏的对话样本，会持续把模型带偏。改完卡继续用旧聊天，你会发现「怎么改了还是那样」

改卡前想先看看有没有问题，可以只校验不部署：

```bash
node scripts/deploy_card.js -i card.json -d <目录> --dry-run
```

### 另一种方式：做成 PNG 卡

上面那个脚本是把 JSON 拷进酒馆的目录。**如果你想要一张能直接拖进去的卡**（还自带头像），
把 JSON 打包成 PNG：

```bash
python json2png.py -i 你的角色卡.json -o 你的角色卡.png --avatar 头像.png
```

没有头像图也能跑——会生成一张渐变占位图，之后在酒馆里再换。

PNG 卡的原理是：角色卡数据以 base64 塞在图片的 `tEXt` 文本块里。这个脚本**两个块都写**
（`chara` 是 V2、`ccv3` 是 V3），新旧版本的酒馆都能读出来。

> ⚠️ **别用微信发 PNG 卡。** 微信会重新压缩图片，`tEXt` 块会丢，卡就废了。要发就发 JSON。

### 关于卡片规范：V2 还是 V3

酒馆的卡片规范有三代，**三代都能导入**：

| 版本 | 特点 | 什么时候用 |
|---|---|---|
| V1 | 六个平铺字段，没有世界书、没有多开场白 | 老卡 |
| **V2** | 信封结构 + 世界书 + 多开场白 | **本项目的输出。所有版本都能读，最稳** |
| V3 | 在 V2 之上加 `assets`（立绘 / 语音）、`nickname`、多语言备注、`.charx` 容器 | 需要立绘或语音时 |

酒馆**读 V3 优先**，但 V3 本身就向后兼容 V2——所以只带 V2 字段的卡完全能用。
`validate_card.py` 三个版本的 `spec` 都认，会直接告诉你正在校验哪一种。

## 九维度统计的是什么

`analyze.py` 输出以下九项，每一项都是角色卡里某个设定的依据：

| # | 维度 | 用途 |
|---|---|---|
| 1 | 消息长度分布 | 决定「说话碎不碎」 |
| 2 | 每月消息量 | 关系热度曲线，用于背景设定 |
| 3 | 活跃时段 | 决定角色什么时间最活跃 |
| 4 | 方括号表情 + 摊薄率 | **铁律二的数据来源** |
| 5 | Unicode emoji 排行 | 同上 |
| 6 | 口头禅候选 | 填 personality 栏 |
| 7 | 高频词片段 | 补充语言特征 |
| 8 | 句尾习惯 | 细化语气 |
| 9 | 连发密度 | 决定「一个回合发几条」 |

## 伦理与边界

这个项目做的是**用数据描述一个人的说话方式**，这件事本身有明确的风险，请认真对待：

- **取得同意。** 如果你要复刻的是另一个人的说话方式，请先确认对方知情并同意。这不是客套话——把一个人的说话方式做成可无限调用的副本，和发布他的照片是同一量级的事。
- **不要把真实人物卡公开发布。** 你要分享的是方法，不是某个具体的人。
- **不用于欺骗。** 不要用生成的副本冒充真人进行对话、获取信任或任何形式的欺骗。
- **数据留在本地。** 本管道全程离线运行，不会上传任何数据。请保持这一点。

## 发布 / 提交之前

要 fork、要往仓库里加自己的东西、或者 push 之前，**先跑一次自检**：

```bash
python scripts/check_privacy.py
```

它会扫一遍**将要交给 git 的文件**，看有没有夹带手机号、微信号、本机路径、密钥之类的东西。
被 `.gitignore` 忽略的文件不扫——那些本来就进不了仓库。命中会列出文件、行号和内容并返回退出码 1；干净则返回 0。

> ⚠️ **它挡不住 git 历史。** 真实数据一旦提交过，删掉文件也还留在历史里。
> 所以顺序永远是：**先确认干净 → 再 `git add`**。
