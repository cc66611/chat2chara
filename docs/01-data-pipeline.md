# 数据管道详解

> 所有脚本默认输出中文，加 `--lang en` 可切成英文。

## 为什么要规范成统一格式

聊天记录的导出格式五花八门：有的是数组，有的包在 `messages` 里；时间字段有的叫 `time`、有的叫 `timestamp`、有的叫 `createTime`；发言人字段有的叫 `sender`、有的叫 `from`、有的叫 `talker`。

如果每个脚本都自己解析一遍，改一处要动全身。

所以第一步统一转成**管道标准格式**——三行一组，空行分隔：

```
2024-03-01 20:15:00
小鱼
在呢

2024-03-01 20:15:30
阿木
吃饭了吗

```

**为什么用这种看起来有点笨的格式，而不是 JSON 或 CSV？**

因为后面要人工看、要喂给 LLM。这种格式：

- 肉眼扫过去很自然，段落之间有空行，读起来像剧本
- 时间、发言人、内容各自独占一行，正则和字符串匹配都很简单
- 直接 `cat` 出来就能贴给任何 LLM，不需要解释格式

代价是文件偏大、解析时要按 4 行步进。对这个场景来说是划算的。

## json2txt.py

### 支持的输入结构

```jsonc
// 形式一：裸数组
[{"time": "...", "sender": "...", "content": "...", "type": 1}, ...]

// 形式二：包一层
{"messages": [...]}
{"data": [...]}
{"chat": [...]}
{"records": [...]}
```

如果是形式二但键名不在候选列表里，脚本会退而求其次：**找所有 value 是数组的键，取最长的那个**。大多数导出格式都能被这个策略兜住。

### 字段映射

每个字段都有一组候选键，按顺序取第一个非空的：

| 目标 | 候选键 |
|---|---|
| 时间 | `time` / `timestamp` / `createTime` / `date` / `ts` |
| 发言人 | `sender` / `senderName` / `from` / `talker` / `nickname` / `name` |
| 内容 | `content` / `text` / `message` / `msg` |
| 类型 | `type` / `msgType` |

已处理的平台差异（踩过的坑）：

- **分段数组文本**：Telegram 等平台把富文本存成数组，形如
  `"text": ["今天", {"type": "bold", "text": "超累"}]`。
  转换时会按片段拼接成 `今天超累`，而不是留下一串 Python 字面量。
- **ISO 时间**：`2024-03-01T21:22:00` 里的 `T` 会自动换成空格，统一成管道惯用的 `2024-03-01 21:22:00`。
- **消息类型**：Telegram 用 `"type": "message"` 标记普通消息，已加入白名单；
  `"service"`（入群、改群名之类的系统消息）会被跳过。

### 先看清有哪些发言人

在正式转换前建议先跑一次：

```bash
python json2txt.py -i your_export.json --list-senders
```

输出会按消息量排序，列出所有发言人。**这一步很重要**——你要从里面认准「哪个名字是对方、哪个是本人」，后面所有脚本都要用这两个名字。

如果里面出现了系统提示、广告号、群成员等杂项，说明这份导出里混了非目标会话的内容，需要先清理。

### 非文本消息怎么处理

图片、语音、表情包、转账这类消息没有可分析的文本，但它们**占据着对话的位置**。

如果直接丢掉，上下文会断裂。举例：

```
小鱼：我今天不开心
[图片]
小鱼：你看这个
```

丢掉中间那条，后两句就接不上了。

所以默认行为是**保留为占位标记** `[图片]`，让位置和节奏还在。这些标记在 `analyze.py` 里会被单独识别（`[4] 方括号表情排行`只统计它们），不会污染语言风格的统计。

### 校验机制

转换完会打印两个数字：

```
对方名「小鱼」出现行数：1671
本人名「阿木」出现行数：1329
```

这两个数字应该**和两人各自的消息条数吻合**。如果差得远，说明名字没对上（比如导出里用的是备注名而不是昵称），要回头用 `--list-senders` 重新确认。

## analyze.py：九个维度

这一步是整个管道的价值所在。它**不调用任何 LLM**，纯统计。

### 为什么不用 LLM 做这一步

可以问，但没必要，而且有坏处：

1. **LLM 数不准。** 20 万条消息它读不完，读个采样又会有偏差。而统计要的是精确计数。
2. **LLM 会美化。** 它倾向于概括成「活泼开朗、偶尔撒娇」这种正确的废话，而你要的是「某个词出现了 892 次」这种可用的数字。
3. **成本。** 本地统计零成本，跑一次几十秒。

LLM 应该用在最后一步——**读采样片段，把统计数字组织成有血肉的人物设定**。分工是：统计负责「是什么」，LLM 负责「怎么讲」。

### 九个维度逐项说明

**1. 消息长度分布**

分四档：≤5 字 / 6-20 字 / 21-100 字 / >100 字。

这一项直接决定角色卡里「说话碎不碎」这条设定。如果 90% 的消息都在 5 字以内，那角色卡的 `personality` 第一条就该写「说话极短极碎」。

**2. 每月消息量**

画出关系热度曲线。

这一项不是给模型用的，是**给你自己用的**——它能帮你判断哪些时间段的数据有代表性。如果某个月只有 100 条，那个月的采样就不该占太大权重。

**3. 活跃时段**

按小时统计。

决定角色的作息设定。是深夜型还是早起型，这一项说了算。

**4. 方括号表情 + 摊薄率** ★

最有用的一项。

输出格式：

```
[亲亲]       × 892       每 214 条出现 1 次
```

那个「每 214 条出现 1 次」就是摊薄率，**直接抄进角色卡的指令里**。

这是铁律二的落地方式：不要写「偶尔用」，要写「平均每 214 条才出现 1 次，绝大多数回复禁止使用」。模型对数字的服从度远高于对形容词的服从度。

**5. Unicode emoji 排行**

和上一条同理，只是对象是系统 emoji（😡🥺😭 这类）。

**6. 口头禅候选**

统计重复出现的**完整短句**（2-8 字，出现过至少 N 次）。

为什么限定完整短句而不是词？因为口头禅的特征是**独立成句**——「摸摸」「嗯哼」「好叭」这类。它们能独立发出来，所以统计整体匹配比词频更准。

`--phrase-min` 可以调阈值，样本少的时候调低。

**7. 高频词片段**

2-4 字的 n-gram，带停用词过滤。

这一项补充第 6 项的盲区——那些不成句但反复出现的搭配。

**8. 句尾习惯**

统计句尾标点和语气词。

细化语气用，比如「她的问句经常不带问号」「她句尾爱带『嘛』」。

**9. 连发密度** ★

统计「角色一个回合平均发几条消息」。

这一项经常被忽略但非常重要。它决定的是**节奏**——不是单条多长，而是一次发几条。

输出会给出分布：

```
平均 2.26 条/回合 | 最长 14 条
1 条连发：321 次
2 条连发：180 次
3 条连发：110 次
```

有了这个，「偶尔连发两三句」就有依据了：`personality` 里写「一件事拆成两三条连发，很少超过四条」，而不是拍脑袋。

## sample.py：为什么必须采连续片段

### 为什么不能随机抽句子

角色卡的核心目标之一是让模型学会**「对方怎么接话」**。

接话这个能力只存在于上下文里。单独抽一句「嗯」出来，模型学不到任何东西；但如果你抽的是：

```
阿木：我今天不太舒服
小鱼：咋了
小鱼：哪里不舒服
小鱼：摸摸
小鱼：没事儿
小鱼：早点睡
```

模型就能看出：对方说不舒服时，她会连发几条短句，先问、再安慰、最后催睡觉。

**这就是为什么采样要取连续片段，而不是随机句子。**

### 时间分层加权

同时还要避免另一个陷阱：**只抽到热恋期。**

一段关系里不同时期的说话方式差异很大。如果随机采样，消息密集的月份会被抽到大量样本，冷清月份几乎抽不到，最后做出来的卡只有「热恋时的她」。

所以按**月**分桶，然后：

```
每月配额 = 保底条数 + (该月消息量 / 总量) × 剩余额度
```

- **保底**（`--base`，默认 120）：保证冷清月份不被完全丢掉
- **加权**（剩余额度按消息量分配）：保证热月拿到更多样本

这样每个时期都有代表。

### 可复现

`--seed` 默认 42。同样的输入和种子，采样结果完全一致。

这很重要：当你想对比「改了这个参数对卡的影响」，采样必须固定。

### 片段长度 20-45 条

`--seg-min` / `--seg-max` 控制。

太短（比如 5 条）会丢掉上下文；太长（比如 100 条）会让单个片段里话题漂移，一个片段混了好几个话题。

20-45 条大致对应一次完整的对话往返。

## 精读这一步怎么做

`sampled.txt` 是给 LLM 读的原料。建议：

1. **分批喂。** 一次喂完太多会稀释注意力。按片段分批，每批让 LLM 输出固定结构的提炼结果。
2. **给明确的输出结构。** 比如固定输出「高频词 / 情绪模式 / 特殊习惯 / 典型对话示例」四栏，这样多批结果好合并。
3. **和 stats.txt 交叉验证。** LLM 提炼出的特征，去 `stats.txt` 里找对应的数字。找不到数字支撑的，要么删掉，要么标记为「待确认」。

**最终判断标准**：角色卡里的每一条设定，都应该能回答「依据是什么」。答不上来的条目，就是在编。
